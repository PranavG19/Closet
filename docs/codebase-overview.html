closet·app — codebase overview

A women's premium wardrobe app: point it at your camera roll, watch your real closet get digitized privately in seconds, then pay to unlock it. This document explains what exists, what is proven, and — honestly — what is still missing.
Expo / React Native pnpm monorepo TypeScript strict Supabase (Postgres + RLS + Edge) RevenueCat vitest + testcontainers mostly AI-coded
How to read this. Every claim here was re-derived by reading the actual code, migrations and tests — not from a checkbox in a doc. This repo's own culture is that a [x] is a claim to re-verify, not a fact. The current working state is branch fix/outfits-concurrent-create with a large body of uncommitted in-flight mobile work (the onboarding/photo-intake pieces). Where something is built-but-unproven-in-production, it says so.

01 What this app is

closet-app turns a phone camera roll into a searchable, organized digital wardrobe. The conversion thesis is a controlled reveal: a woman grants photo access; an on-device gate filters out intimate / non-her photos before anything is uploaded; a handful of items are parsed in the cloud in real time (attributes + a clean cut-out); she sees her actual clothes digitized within ~30 seconds — the "aha" — and hits a hard paywall, no free trial. After payment the rest of the roll is parsed. The daily hook is answering "what do I wear today" (weather-aware suggestions from what's clean), and the moat is the wear log — a timestamped record of what she actually wore that no competitor can backfill.

Engineering is deliberately backend-first ("prove data + RLS + endpoints before UI") and the codebase is built to be worked on by AI agents — so its defining discipline is manufacturing verification signals the coding agent could not itself produce (real Postgres with RLS enforced, real webhook payloads, simulator screenshots, mutation probes). The product spec lives in docs/00–05; the operating model in docs/04; the honest launch audit in docs/LAUNCH-READINESS.md.

Two paths bypass the Edge tier by design: the app talks directly to Supabase Storage for photo bytes (upload originals, download cut-outs) under Storage-RLS — never through Edge CPU — and the RevenueCat webhook is a server-to-server route with no user JWT (it authenticates the sender by a constant-time shared-secret and is the sole writer of the money table via service_role). The morning "what do I wear" loop runs entirely on-device (harmony, suggestions, palette, dedupe are pure functions in shared), so 100k users cost zero server compute for it.

The privacy invariant (the app's defining constraint). The on-device gate filters intimate / non-her photos before any upload. There is deliberately no server-side gate — a server filter would already have received the photo. "You cannot leak what never left the device." This is structural (ABLATE-tier), not a "please delete" promise. The server literally cannot distinguish an approved photo from an unapproved one; the guarantee is enforced on-device as "no upload without an explicit approval tap" (see the ApprovedPhoto brand in §10). Adjacent invariants: body geometry (future try-on) is session-ephemeral (no server body-twin), and skin tone is self-identified via a swatch quiz, never camera-detected.

The disciplines that keep it safe

  • Repos are the only DB path. packages/db/src/repos/ — account · export · outfit-items · outfits · palette · parse-jobs · rate-limit · subscriptions · wardrobe · wear-log · webhook-events. Handlers compose them; they write no SQL.
  • parse-don't-cast. Every DB row, request and response passes through a Zod schema (parseBoundary). No as casts across trust boundaries. Repos cast timestamptz→::text and numeric→::float in SELECT so rows match schemas and survive JSON.stringify.
  • client_id idempotency. The caller mints client_id at tap time and passes it in — never inside the mutation function, where a retry would create duplicate rows. A partial UNIQUE index dedups retries onto the caller's own row.
  • Migrations are append-only + reversible. Never edit a landed migration; destructive DDL needs a human approval token under migrations/approvals/ (a directory that does not exist yet — the mechanism is declared, never exercised). Round-trip DOWN on populated data is a human-gated step that has never run.
  • One sanctioned RLS bypass: makeServiceExecutor (the webhook only) runs as service_role with no SET LOCAL ROLE — the single system-jobs seam. Every other executor is per-request app_user.

05 The rules & non-negotiables

The codebase is organized around five "agent-arch" rules plus a set of security invariants. The five rules govern how work is done; the invariants govern what must always hold.

The five rules

  1. One pass or decompose. If change + tests + verification don't fit one context window, split first.
  2. Make the unsafe thing unrepresentable. Push enforcement below the app layer: DB RLS FORCE > tsconfig/lint > tests. Make bad states impossible, don't just test for them.
  3. Verify from a vantage you cannot reach. Real simulator screenshot for UI; red-first test with an oracle you didn't compute for logic; real webhook for money. A test the same agent wrote is a mirror oracle, not verification.
  4. The safe path is the fast path. Gates run affected-only in seconds; don't ship a gate adding >10% latency.
  5. Stop on the escalation trigger. Irreversible ops, money/entitlement, or unobservable visual output → request human review. (The money path has an explicit autonomy grant — see below.)

Security invariants

  • Repos are the only DB path; supabase.from() banned elsewhere.
  • Identity from the verified JWT sub via withAuth/serveAuthed (asymmetric JWKS — no shared secret), never a request body.
  • RLS FORCE + default-deny on every tenant table; service_role only for system jobs.
  • Colors from useTokens(), never literal hex.
  • Structured logger only, never console; never log raw error messages (PII).
  • Read env via envValue()/requireEnv(), never bare process.env (Edge runs Deno).
  • Secrets live in gitignored .env.* — source them, never read them into context.
  • The on-device gate runs before any upload.
Honesty about enforcement — this repo is unusually candid about it. Several of the invariants above are held by discipline and review, not by a mechanical gate. There is no CI (.github/ contains only CODEOWNERS); the only automated enforcement is a local pre-commit hook + a handful of gates in scripts/verify.mjs. Specifically absent despite being described elsewhere as gates: the no-literal-colors gate, the supabase.from() lint-ban, no-console, the cross-feature-import ban, the bare-process.env ban, and a pnpm mutation battery. The behavior is currently clean by discipline. The "agent cannot edit its own cage" rule (human-owned conventions.json, hooks, gate scripts…) is generated into CODEOWNERS but marked PARKED — not enforced until a GitHub remote exists, and there is no remote; the real enforcement is the per-agent prompt.
Money path — autonomy granted (2026-08-06). Overriding Rule 5's default, CLAUDE.md grants full build/verify/commit/merge autonomy on the RevenueCat/entitlement path (there is no remote; the owner reviews commits directly). The verification bar is unchanged: entitlement must be proven against a real webhook event, never a mocked success — and that real-event verification still has not happened.

08 Path to launch / showing investors

There is no path today from "a woman installs this" to "she pays," because F1 (the reveal) and F2 (the purchase) are both incomplete and nothing is deployed. Ordered minimum to reach an end-to-end demoable flow — [H] human-required, [A] agent-doable, [A→H] agent builds / human gates:

  1. [A]Finish + re-capture the visual fixes. Safe-area insets, tab label, AA palette, typeface are coded but unconfirmed; re-shoot on a booted sim (the oracle). Cheapest high-value work, needs nothing from anyone.
  2. [H]Pick a product name. "[App Name]" is a live token in ~9 content files; blocks all listings/ASO.
  3. [H→A]Decide pricing + create the RevenueCat / App Store product, then wire the real purchase call and put price + renewal terms on the paywall. Without this the build is rejected and cannot charge.
  4. [H]Provision provider API keys (OpenAI, Photoroom). Adapters are built and waiting; this is the only thing between them and a real parse.
  5. [A→H]Stand up a real Supabase project. Wire DATABASE_URL (app_user), SUPABASE_DB_SERVICE_URL (real service_role), JWKS_URL, the webhook secret; create originals+cutouts buckets; apply all 16 migrations; re-prove Storage RLS on real Storage. Run the preflight suite (14 tests self-skip until a real project ref is set). Watch the two silent-failure traps: a mis-wired service_role makes the webhook 500 and paying users stay locked out; Storage RLS must actually bind to sub.
  6. [A→H]Ship F1: the scan→reveal flow + the on-device privacy classifier. The in-flight photo-intake work is the skeleton; the classifier is a hard launch blocker (agent builds the model/harness; human curates the labeled corpus and owns the safety go/no-go). Strip EXIF/GPS on-device before upload — not a present defect (no upload path yet) but becomes one instantly (a wardrobe photo's GPS = a home address forwarded to two vendors).
  7. [A]Grade real parse quality against the bench-scan corpus with live providers — the first honest measurement of the make-or-break lever.
  8. [A]Fill the remaining UI gaps (F4 filters + dedupe pick, F6 builder canvas, F7's two transitions, B1 quiz, F3 full-parse UI) — all backend-complete, all UI-absent; five dead mutation hooks get callers.
  9. [A→H]Verify money against a real RevenueCat event and round-trip every migration DOWN on populated data — the two external oracles that have never run.
  10. [A→H]Publish SEO, legal sign-off, App Store submission with fresh screenshots.
Critical path to a build that survives review: 1→2→3.  To a usable product: +4→5→6.  To an honest launch: +7, 9, and the classifier recall floor in 6 — the external oracles that still have never run.

09 Testing story

Because the code is mostly AI-written, its tests are too — the "mirror oracle" problem: the author grades the author, and a green suite can encode the exact wrong assumption the code does. The entire test framework (docs/05) is therefore organized not by feature but by how independent each tier's grading signal is from the author.

The vitest lanes

  • unit (packages/*/src/**/*.test.ts) — pure logic + property-based tests via fast-check. Runs in ~seconds.
  • integration (test:integration) — real Postgres via testcontainers, the full migration chain applied, RLS enforced. The mandatory discipline: every test SET LOCAL ROLE app_user, because the container superuser bypasses RLS — forgetting it proves nothing.
  • perf (test:perf, not in the gate wall) — times the 10 repo ops against a populated wardrobe, 200 samples, asserts p95 vs SLOs. The measured finding was honest: every DB op is p50 4–8ms / p95 10–23ms noise — nothing to optimize at the DB layer; real latency is the undeployed provider calls + RN render.

What this discipline actually caught (each re-derived from main, not trusted from a build agent's green report): a teaser-cap race that let 12 requests past a cap of 3 (a snapshot-read an advisory lock can't rescue); a wear-log 500 under simultaneous taps; a cross-tenant photo-read + SSRF on the parse path (a body-supplied path handed to vendors); a permanently-bricked photo after a crashed parse; the money-gate and secret-auth mutants; and a zod specifier missing from the Deno import map that would have killed all 12 deployed functions at load. The strongest external oracles — a real webhook delivery, real Storage RLS, real provider output, a populated-migration round-trip — have still never run.

10 Notable code & honest smells

The color-harmony wheel — packages/shared/src/harmony.ts

Twelve chromatic hue families on an evenly-spaced HSL wheel plus five neutrals. The verdict for any pair is driven by circular hue distance, computed once per unordered pair to build a frozen lookup table keyed by the sorted pair — so harmony(a,b) and harmony(b,a) read the same cell and symmetry is structural, not tested-for. It also correctly distinguishes triadic (120°) and split-complementary (150°) from a genuine clash, and the comment warns the next reader not to "fix" it to the RYB painter's wheel.

// circular distance on the 12-hue wheel drives the verdict; a frozen table makes it total + symmetric
function verdictFor(a, b) {
  if (NEUTRAL_SET.has(a) || NEUTRAL_SET.has(b)) return 'neutral';
  const raw = Math.abs(HUE_INDEX.get(a) - HUE_INDEX.get(b));
  const distance = Math.min(raw, 12 - raw);         // 0..6
  if (distance === 6) return 'complementary';      // 180°
  if (distance === 4) return 'triadic';            // 120°
  if (distance === 5) return 'split-complementary'; // 150°
  return 'clash';                             // 60° / 90° — genuinely weaker
}

The concurrent-idempotency wear-log — packages/db/src/repos/wear-log.repo.ts

The append is one statement (one tx per query): a writable CTE that inserts ON CONFLICT DO NOTHING on the partial UNIQUE(user_id, client_id), and flips the item to dirty only when a new row landed. The subtle bit: it deliberately does not use an in-statement UNION ALL fallback, because under READ COMMITTED the loser's snapshot is taken before the winner commits — so on a truly-simultaneous duplicate tap the fallback would see zero rows and 500. Instead, on conflict it re-reads in a fresh query() (a new transaction = a new snapshot that sees the committed winner). This exact trap was found by the chaos suite and later re-found in outfits.repo.

The privacy approval-brand — packages/shared/src/approvedPhoto.ts ◆ uncommitted

The most interesting single file in the in-flight work. Since the server cannot tell an approved photo from an unapproved one, "no upload without approval" is enforced on-device as a type: ApprovedPhoto is branded with a module-private unique symbol that is never exported, so it can only be produced by approvePhoto(), which requires the tapped+screened photo and refuses any verdict but candidate. Because a TS brand is erased at runtime, it adds runtime backstops the code comments trace to specific red-team launderings: Object.freeze kills the mutation route, and the upload chokepoint re-derives the SHA-256 digest and refuses bytes that don't hash to their key. The file is careful to say what it does not do — it does not classify; whether the model catches intimate photos is a recall metric graded against an independent corpus, which the human owns.

The parse-photo privacy + money seam — packages/functions/src/parse/parse-photo.ts

A pure orchestrator (writes zero SQL) that layers the money-adjacent guarantees in order: entitlement gate first (402 on kind=full), then the per-user spend throttle (a 429 costs zero provider dollars and zero rows), then an atomic job-claim (one winner, never a double-charge), then the provider calls, then an atomic commit. The load-bearing security fix lives here: the source-photo path is derived server-side from the verified sub as {user_id}/{hash}/original and stripped from the request schema (.strict()) — because the vendors fetch the photo from a URL on their own servers, so no Postgres RLS policy can reach that fetch. Making the path unrepresentable in the request closed a real cross-tenant read + SSRF.

Honest smells & fragile patterns found while reading

Live: JWT verification omits required claims. withAuth.ts:63 calls jwtVerify(token, jwks) with no options — the 2026-08-09 review empirically proved a token with a hostile iss, wrong aud, or no exp at all still verifies and returns its sub (a permanent credential). The fix ({ issuer, audience, requiredClaims:['exp'] }) was "assigned to the security branch" but is not present on this working branch; the file's own comment ("issuer/audience are optional additional checks") is part of the defect. Worth confirming this landed before any deploy.
  • Tests under features/** silently never run. The vitest unit project globs packages/*/src/**; a test placed under features/ is not skipped — it never executes. This already bit a 20-test billing suite. Flagged, not fixed (widening the glob is adjacent shared config).
  • "Gate" vs reality gap. Multiple docs describe lint gates (no-literal-colors, supabase.from() ban, no-console, cross-feature imports) that do not exist; there is no CI. The invariants hold by discipline. The repo is admirably honest about this in LAUNCH-READINESS.md §4 — but a reader trusting the older docs would over-estimate the safety net.
  • The cage is advisory. The "agent cannot edit its own guardrails" rule is generated into CODEOWNERS but explicitly PARKED (no remote). Real enforcement is the per-agent prompt.
  • Doc-count drift. Migration/route/test counts are hardcoded across ~8 docs and have drifted repeatedly; the durable fix (a generated STATUS.md or a check-doc-counts gate) is identified but unbuilt.
  • Environment friction. pnpm add fails in this repo (the prepare script's lefthook install refuses under a global core.hooksPath), so deps must be hand-added to package.json and reconciled with --lockfile-only — a real footgun for the next contributor. Also both .env.example files are untracked while the runbook cites them as authoritative.
What's genuinely good, to balance the smells: the composite-FK design makes cross-user references unrepresentable at the schema level rather than validated; the append-only moat is enforced by grant matrix, not convention; the money table has no app_user write policy at all; and the codebase's willingness to write down its own gaps (RUN-LOG, LAUNCH-READINESS) is unusually disciplined — it treats a passing test as a claim to re-derive, which is exactly right for AI-authored code.
