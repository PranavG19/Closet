# Task: parse-photo — atomic claim + provider calls + commit fn + teaser cap + entitlement gate

**slug:** `task-13-parse-photo`
**wave:** 4
**reversibility:** reversible

## 1. Intent

`parse-photo` is the make-or-break endpoint: the one place that holds the vision + cutout provider secrets, turns an approved photo into garment rows, and enforces the two money-adjacent server guarantees — the **hard per-user teaser cap** and the **entitlement gate on `kind=full`**. It must be **idempotent and resumable** with zero extra infra (no queue, no worker): a photo re-submitted after a crash mid-parse creates **no duplicate garments**, and two concurrent invocations on the same photo produce **one winner**, never a double-charge to the paid providers or a double-insert.

The whole endpoint is built from four moves, in order (docs/06 §4):
1. **Idempotent job resolve** — `INSERT … ON CONFLICT (user_id, source_photo_hash) DO NOTHING` then read back the row, so re-submit of the same photo lands on the same `parse_jobs` row (the idempotency key lives on the photo, never on items).
2. **Atomic claim** — a single conditional `UPDATE … SET status='processing', claimed_at=now() WHERE id=? AND status IN ('pending','failed') AND (claimed_at IS NULL OR claimed_at < now() - interval '2 min')`. Proceed **only if rowcount = 1**; a lost race returns "already in progress" and never reprocesses. `claimed_at` is the crash lease.
3. **Provider calls** — `AIVisionPort.extractAttributes` (attributes) + `CutoutPort.removeBackground` (cutout), called only from here, behind the ports so parse quality is A/B-swappable against the bench-scan oracle.
4. **Atomic commit** — one single-statement commit: **delete any partial items by `parse_job_id`**, insert the new items, set `status='done'` — atomically, so a prior failed job's partial rows are cleaned before reprocess and retries never double-insert.

Layered on top: `kind=full` first verifies `subscriptions.entitlement_active` and **402s** otherwise; `kind=teaser` skips entitlement (that is its point) but is bounded by a **hard per-user teaser-job cap** enforced by an atomic counter on `parse_jobs WHERE kind='teaser'`, because identity is established up front and every teaser row is written under a real authenticated `user_id`.

## 3. Technical requirements (numbered, dependency-ordered)

1. **`packages/functions/src/parse/parse-photo.ts`** — `export const parsePhoto: AuthedHandler`. Orchestrates the four moves below over `ctx.exec` and the injected repos. Parse the request body with `parseBoundary(CreateParseJobRequest, body)` (`{ source_photo_path, source_photo_hash, kind }`, `.strict()`, carries **no** `user_id`). `user_id` is always `ctx.userId`.

2. **`packages/functions/src/parse/teaser-cap.ts`** — `export const TEASER_JOB_CAP = 10;` (the hard per-user cap on `parse_jobs WHERE kind='teaser'`; docs/06 §4 + docs/05 Tier-0 names this constant as the mutation target `10→1000`). Exported as a single named constant so the mutation battery can target it and the handler + test read the same value. No other logic in this module.

3. **Entitlement gate (`kind='full'`), FIRST, before any claim or provider call.** Read entitlement via the subscriptions repo (`readEntitlement(userId) → { entitlement_active, expires_at } | null`); if `kind==='full'` and `entitlement_active !== true` (a missing row counts as not entitled), return `errorResponse(402, 'entitlement_required')` and do nothing else — no job row, no provider call. `kind='teaser'` skips this check entirely.

4. **Teaser cap (`kind='teaser'`), enforced atomically at job resolve.** For `kind='teaser'`, resolving a *new* teaser job must fail if the user already holds `TEASER_JOB_CAP` teaser jobs. This MUST be atomic against concurrent teaser submissions (two different new photos racing must not both slip past the cap) — enforced inside the repo's job-resolve statement (a conditional insert whose count is evaluated under a per-user `pg_advisory_xact_lock`, so the count-then-insert is serialized per `user_id`). Re-submitting an **already-existing** photo (same `source_photo_hash`) is idempotent and does **not** count against the cap (it lands on the existing row). When the cap is hit for a genuinely new photo, return `errorResponse(402, 'teaser_cap_reached')`.

5. **Idempotent job resolve.** Via the parse-jobs repo `resolveJob({ userId, sourcePhotoHash, sourcePhotoPath, kind })`: `INSERT … ON CONFLICT (user_id, source_photo_hash) DO NOTHING`, then read back and return the `ParseJobRow`. Re-submit of the same photo returns the same row (idempotency key on the photo, per docs/06 §3). If the resolved job is already `status='done'`, **short-circuit**: return `jsonResponse(200, …)` with the existing items for that `parse_job_id` (idempotent replay — no re-claim, no provider call, no double-charge).

6. **Atomic claim.** Via the parse-jobs repo `claim(jobId) → { claimed: boolean }` implemented as the single conditional `UPDATE … SET status='processing', claimed_at=now() WHERE id=$1 AND status IN ('pending','failed') AND (claimed_at IS NULL OR claimed_at < now() - interval '2 min')` returning affected rowcount. Proceed **only if rowcount === 1**. If `claimed === false` (lost race / already processing within the lease), return `errorResponse(409, 'parse_already_in_progress')` — never reprocess.

7. **Provider calls, only after a successful claim.** Build the provider input from the approved original (`source_photo_path` → the `imageUrl`/storage reference the ports expect). Call `AIVisionPort.extractAttributes` and `CutoutPort.removeBackground`. Map the Zod-validated results into `wardrobe_items` insert rows: `category` ← vision category; `color` ← `primaryColor`; `pattern` ← vision pattern; `attributes` (jsonb) ← `{ secondaryColors, material, formality, season }`; `cutout_path` ← `CutoutResult.imageUrl`; `parse_job_id` ← the job id; `phash` is on-device-only and stays null on the server path. Ports are obtained via a factory/DI seam so the integration test can inject deterministic fakes (real GPT-4o/Photoroom adapters are out of scope; port construction reads secrets via `envValue`).

8. **Atomic commit.** Via the parse-jobs repo `commit({ jobId, userId, items }) → { itemCount }` — a **single data-modifying CTE**: `WITH del AS (DELETE FROM public.wardrobe_items WHERE parse_job_id=$1), ins AS (INSERT INTO public.wardrobe_items (…) SELECT … ) UPDATE public.parse_jobs SET status='done' WHERE id=$1`. Delete-partial-then-insert makes reprocess of a `failed`/`processing` job idempotent (no double garments). Return `jsonResponse(200, parseBoundary(ParseResultResponse, { job, items }))`.

9. **Failure path.** If a provider call throws / times out, mark the job `status='failed'` with a **fixed `error_reason` string** (no PII, no raw provider message) via the parse-jobs repo `markFailed(jobId, reason)`, log with `correlationId` via the structured logger, and return `errorResponse(502, 'parse_provider_failed')`. Because `claim` allows `status IN ('pending','failed')` and `commit` deletes partial items first, a later resubmit re-claims and cleanly reprocesses. (Degraded fan-out — reveal succeeded items rather than a spinner — is a client concern per docs/06 §4; do not build a spinner/queue here.)

10. **Response schema (`packages/functions/src/parse/parse-photo.ts` or a local `schemas`-free reuse):** the success body is validated with a response schema composed from `ParseJobRow` + `WardrobeItemRow[]` already exported by `@closet/shared` (`parseBoundary` on the way out). Do **not** author new row schemas — reuse `@closet/shared`. If a thin `ParseResultResponse` wrapper object is needed and does not exist in `@closet/shared`, define it locally in this file over the imported row schemas (this task cannot touch `packages/shared`); flag if a shared schema would be preferable.

11. **Deno shim** — if the repo/handler split requires an entrypoint, note that the `supabase/functions/parse-photo/index.ts` shim (`serveAuthed(parsePhoto)`, ~3 lines) is **out of scope for this task's file allowlist** (`supabase/functions/**` is not `packages/functions/src/parse/**`); flag it as a follow-up owned by the deploy-wiring task. Author only the built handler here.

**Repo-method contracts this handler depends on (owned by task-09-repos in `@closet/db`; enumerated here so they can be provided/added):**
- `makeParseJobsRepo(exec)` → `resolveJob({ userId, sourcePhotoHash, sourcePhotoPath, kind }) → Promise<ParseJobRow>` (idempotent upsert + teaser-cap-atomic for `kind='teaser'`), `claim(jobId) → Promise<{ claimed: boolean }>`, `commit({ jobId, userId, items }) → Promise<{ itemCount: number }>`, `markFailed(jobId, reason) → Promise<void>`, `listItemsByJob(jobId) → Promise<WardrobeItemRow[]>`, `countTeaserJobs(userId) → Promise<number>`.
- `makeSubscriptionsRepo(exec)` → `readEntitlement(userId) → Promise<{ entitlement_active: boolean; expires_at: string | null } | null>`.

## 4. Acceptance criteria (Given-When-Then)

- **Teaser happy path:** Given `kind='teaser'` and a user under the cap, When `parsePhoto` runs with a fresh `source_photo_hash`, Then providers are called once, exactly the mapped item(s) are inserted with `parse_job_id` set, the job is `status='done'`, and a 200 body validates against the response schema.
- **Full happy path:** Given `subscriptions.entitlement_active=true` for the caller (written as `service_role`) and `kind='full'`, When `parsePhoto` runs, Then it proceeds through claim → providers → commit and returns 200.
- **Entitlement gate (402):** Given `kind='full'` and **no** subscriptions row (or `entitlement_active=false`), When `parsePhoto` runs, Then it returns `402 entitlement_required`, calls **no** provider, and writes **no** `parse_jobs`/`wardrobe_items` row (independent SELECT count = 0).
- **Teaser cap holds (402):** Given a user already at `TEASER_JOB_CAP` distinct teaser jobs, When a new teaser photo is submitted, Then it returns `402 teaser_cap_reached` and no new job/items are written; re-submitting one of the **existing** teaser photos still returns its result idempotently and does not increase the count.
- **No duplicate garments on resume:** Given a teaser job driven to `done` with N items, then forced back to `status='failed'` with a partial item present (crash simulation), When the same photo is re-submitted, Then the commit deletes the partial and re-inserts, and an independent SELECT of `wardrobe_items WHERE parse_job_id=<job>` counts **exactly N**, not 2N, with `job.status='done'`.
- **One-winner concurrency:** Given a single `pending` job, When two claims race on separate connections (same `app_user` sub), Then exactly one observes `claimed=true` (rowcount=1) and the other observes `claimed=false`; the loser returns `409` and no second provider call / second item set occurs.
- **Already-done short-circuit:** Given a job at `status='done'`, When the same photo is re-submitted, Then it returns 200 with the existing items and calls **no** provider (no double-charge), leaving the item count unchanged.
- **Provider failure → failed, resumable:** Given a provider throws, When `parsePhoto` runs, Then the job is `status='failed'` with a fixed non-PII `error_reason`, a `502 parse_provider_failed` is returned, no partial garbage survives a subsequent successful reprocess, and no raw provider message is logged.
- **Identity from JWT, not body:** Given a body smuggling `user_id: B`, When A calls `parsePhoto`, Then the smuggled field is inert (`.strict()` rejects it or it is ignored) and every written row carries `user_id = A` (RLS + `ctx.userId`).

**The oracles (green = all of):**

Green proves the commit's delete-partial + the per-photo idempotency key (not a per-item UNIQUE) hold. 2. **One-winner concurrency:** open two `app_user` connections, begin overlapping transactions, both attempt `claim` on the same `pending` job; assert exactly one `claimed=true` and one `claimed=false`, and that the provider call-counter increments **once**. Green proves the atomic-claim `rowcount=1` gate + the crash lease serialize contenders through Postgres row locks, with no application-level coordination.
3. **Entitlement-gated:** `kind='full'` with no/false entitlement → `402`, provider counter = 0, `parse_jobs`/`wardrobe_items` counts = 0 (independent SELECT). 5. **Control (RLS is live, not bypassed):** a superuser count confirms A's rows exist while a B-executor (`sub=B`) SELECT of A's items returns 0 — the 0 is isolation, not an empty table. And a body-smuggled `user_id: B` writes rows owned by A only.

**What green looks like:** no-dup-on-resume **and** one-winner-concurrency **and** entitlement-gated (402 without entitlement, proceeds with it) **and** teaser cap holds under concurrency — all on the shipping schema/role matrix, with the four mutation targets provably killed and the provider call-counter proving no double-charge.
